A principal mudança será substituir a lógica de manipulação de lista em memória, utilizada até então, por operações de banco de dados usando o ORM SQLAlchemy, configurado na aula anterior. Basicamente, toda vez que havia database[algo] ou len(database), isso foi substituído por comandos session (query, add, commit, delete).

app.py
from fastapi import FastAPI, HTTPException, Depends
from sqlalchemy.orm import Session
from sqlalchemy.exc import IntegrityError
from fast_zero.schemas import UserSchema, UserResponse, UserList, UserPublic, UserUpdate, Message
from fast_zero.database import engine, get_session
from fast_zero.models import User, mapeador

app = FastAPI()

mapeador.metadata.create_all(bind=engine)

@app.post("/users/", status_code=201, response_model=UserResponse, summary="Cria um usuário")
def create_user(user: UserSchema, session: Session = Depends(get_session)): # (1)!

    db_user = User(**user.model_dump()) # (2)!

    try: 
        session.add(db_user)
        session.commit()
        session.refresh(db_user) # (3)!
    except IntegrityError:
        session.rollback()
        raise HTTPException(status_code=400, detail='Username ou Email já existe') # (4)!

    return {
        "message": "Usuário criado com sucesso",
        "user": db_user
    }


@app.get('/users/', response_model=UserList, summary="Retorna todos os usuários")
def read_users(session: Session = Depends(get_session)):
    usuarios = session.query(User).all() # (5)!
    return {'users': usuarios} 


@app.put('/users/{user_id}', response_model=UserPublic, summary="Atualiza totalmente um usuário")
def update_user(user_id: int, user: UserSchema, session: Session = Depends(get_session)): 
    db_user = session.query(User).filter(User.id == user_id).first() # (6)!

    if not db_user: 
        raise HTTPException(status_code=404, detail='User not found') 

    try:
        for key, value in user.model_dump().items():
            setattr(db_user, key, value) # (7)!

        session.commit()
        session.refresh(db_user)
    except IntegrityError:
        session.rollback()
        raise HTTPException(status_code=400, detail='Username ou Email já está em uso') # (8)!

    return db_user


@app.patch('/users/{user_id}', response_model=UserPublic, summary="Atualiza parcialmente um usuário")
def patch_user(user_id: int, user: UserUpdate, session: Session = Depends(get_session)): # (9)!
    db_user = session.query(User).filter(User.id == user_id).first()

    if not db_user:
        raise HTTPException(status_code=404, detail='User not found')

    update_data = user.model_dump(exclude_unset=True) # (10)!

    try:
        for key, value in update_data.items():
            setattr(db_user, key, value) # (11)!

        session.commit()
        session.refresh(db_user)
    except IntegrityError:
        session.rollback()
        raise HTTPException(status_code=400, detail='Username ou Email já está em uso')

    return db_user


@app.delete('/users/{user_id}', response_model=Message, summary="Deleta um usuário")
def delete_user(user_id: int, session: Session = Depends(get_session)):
    db_user = session.query(User).filter(User.id == user_id).first()

    if not db_user:
        raise HTTPException(status_code=404, detail='User not found')

    session.delete(db_user)
    session.commit() 

    return {'message': 'User deleted'}
  1. Essa é a injeção de dependência. O FastAPI chama a função get_session antes de rodar o seu código, abre uma conexão limpa com o banco de dados e entrega essa session pronta para usar.
  2. O método user.model_dump() converte um objeto validado do Pydantic em um dicionário Python comum, como {"username": "ana", "email": "ana@a.com", "password": "123"}. Em seguida, o desempacotamento desse dicionário permite passar suas chaves como argumentos para a classe User do SQLAlchemy, oferecendo um atalho conveniente em vez de digitar User(username=user.username, email=user.email, password=user.password). O resultado, armazenado em db_user, é um objeto ORM que está pronto para ser inserido no banco de dados, mas que ainda reside na memória.
  3. O bloco try inicia uma seção de código onde, se ocorrer algum erro relacionado ao banco de dados, o fluxo de execução será direcionado para o bloco except. O comando session.add(db_user) adiciona o novo usuário à sessão, colocando-o em um estado pendente para futura persistência. Ao chamar session.commit(), o SQLAlchemy gera e executa o comando INSERT INTO users..., enviando os dados para o SQLite. Caso os dados sejam válidos, as informações são gravadas no disco. Por fim, o método session.refresh(db_user) busca o usuário recém-salvo no banco para atualizar o objeto db_user com informações geradas automaticamente, como o id e a data created_at, as quais são necessárias para serem incluídas na resposta.
  4. O bloco except IntegrityError trata situações em que o commit() falha devido a violação de regras de integridade no banco, como tentar cadastrar um e-mail que já existe, quando a coluna possui a restrição unique=True. O comando session.rollback() atua como um "Ctrl+Z", limpando o estado pendente da sessão e revertendo a transação que falhou. Caso essa operação não seja realizada, a sessão permanece bloqueada, o que compromete requisições subsequentes. Por fim, a instrução raise HTTPException(...) interrompe imediatamente a execução da função e retorna um erro HTTP 400 (Bad Request) para o cliente da API, informando o motivo da falha.
  5. O comando session.query(User) informa ao SQLAlchemy que deseja realizar uma consulta na tabela associada ao modelo User. O método .all() atua como um gatilho, executando a consulta SQL correspondente no SQLite, equivalente a um SELECT * FROM users. O resultado da operação é retornado como uma lista de objetos Python, onde cada item representa uma instância do modelo User com os dados de uma linha da tabela. Esses dados são armazenados na variável usuarios.
  6. O comando session.query(User).filter(User.id == user_id) constrói uma consulta SQL equivalente a SELECT * FROM users WHERE id = user_id. O método .first() solicita que o banco de dados retorne apenas o primeiro resultado encontrado, retornando None caso nenhum registro corresponda ao critério especificado.
  7. O método user.model_dump().items() converte o objeto validado do Pydantic em um dicionário e extrai suas chaves e valores, resultando em uma lista de tuplas, como [('username', 'joao'), ('email', 'joao@a.com'), ('password', '123')]. O laço for key, value in ...: itera sobre cada uma dessas tuplas. Dentro do loop, a função setattr(db_user, key, value) é utilizada para alterar o atributo do objeto db_user, que foi recuperado do banco, substituindo o valor do atributo nomeado em key pelo novo valor value. Esse processo permite atualizar os atributos de db_user de forma automática, como db_user.username = 'joao', db_user.email = 'joao@a.com', etc., sem a necessidade de digitar cada linha individualmente. Neste ponto, as alterações existem apenas na memória do Python e ainda não foram persistidas no banco de dados.
  8. O bloco except IntegrityError captura erros que ocorrem durante o laço for, caso o cliente envie um e-mail ou nome de usuário que já esteja associado a outro usuário no banco. Quando isso acontece, o comando session.commit() resulta em um erro que é tratado neste bloco. O comando session.rollback() é utilizado para limpar a sessão do SQLAlchemy, cancelando qualquer atualização que não tenha sido bem-sucedida. Em seguida, a instrução raise HTTPException(...) gera uma resposta de erro HTTP 400 (Bad Request), informando ao cliente o motivo da falha.
  9. Em vez de usar o UserSchema (onde todos os campos são obrigatórios), usamos o UserUpdate. Lá no seu schemas.py, os campos do UserUpdate estão marcados como Optional e com valor padrão None. Isso permite que o cliente envie um JSON só com o "username", ou só com a "password", sem o FastAPI recusar a requisição.
  10. A linha user.model_dump(exclude_unset=True) é crucial nesta rota, pois transforma os dados recebidos em um dicionário, ignorando todos os campos que não foram enviados pelo cliente na requisição. O parâmetro exclude_unset=True do Pydantic é essencial, especialmente porque os campos em UserUpdate são opcionais. Se o cliente fornecer apenas um novo "username", os campos "email" e "password" apareceriam como None. Sem esse parâmetro, o código sobrescreveria inadvertidamente esses campos no banco de dados com valores nulos, resultando em perda de dados. Com exclude_unset=True, o objeto update_data contém apenas as alterações efetivamente propostas, como por exemplo {'username': 'novo_nome'}, garantindo que apenas os dados desejados sejam atualizados.
  11. O laço for key, value in update_data.items(): itera apenas sobre os itens que permanecem no dicionário filtrado na etapa anterior. Dentro desse loop, a função setattr(db_user, key, value) é utilizada para atualizar o objeto db_user na memória. Se o cliente enviou apenas o novo "username", esse loop será executado apenas uma vez, modificando apenas o nome do usuário, enquanto os campos "email" e "password" permanecem inalterados, garantindo que as informações existentes não sejam sobrescritas.
schemas.py
from typing import Optional
from datetime import datetime
from pydantic import BaseModel, EmailStr, ConfigDict

class UserSchema(BaseModel):
    username: str
    email: EmailStr
    password: str

class UserPublic(BaseModel):
    id: int
    username: str
    email: EmailStr
    created_at: datetime

    model_config = ConfigDict(from_attributes=True) # (1)!

class UserResponse(BaseModel):
    message: str
    user: UserPublic

# Removido o UserDB daqui, pois agora usamos a classe User do models.py do SQLAlchemy

class UserList(BaseModel):
    users: list[UserPublic]

class UserUpdate(BaseModel):
    username: Optional[str] = None 
    email: Optional[EmailStr] = None
    password: Optional[str] = None

class Message(BaseModel):
    message: str
  1. Essa funcionalidade permite que o Pydantic aceite objetos ORM do SQLAlchemy, em vez de exigir dicionários para validação. Sem isso, o Pydantic apenas processa dados como dicionários (ex: dados['id']). Com essa capacidade, ele pode acessar os atributos diretamente de um objeto (ex: objeto.id). Isso é fundamental no FastAPI, pois facilita a transformação automática de dados retornados do banco em JSON na resposta da API.

Session¶

A Session atua como um intermediário entre a aplicação FastAPI e o banco de dados SQLite, facilitando a comunicação e a manipulação dos dados. No FastAPI, a criação e o fechamento da Session é gerenciada de forma automática, o que simplifica o manuseio de transações com o banco de dados. Isso é feito por meio da dependência Depends(get_session), que permite que você obtenha uma nova sessão sempre que uma requisição é recebida.

A função get_session é definida para criar uma nova instância da Session toda vez que é chamada. Internamente, ela é configurada para estabelecer uma conexão com o banco de dados e retornar a sessão criada. Quando um endpoint no FastAPI é definido, você pode simplesmente adicionar Depends(get_session) como um argumento. Isso assegura que uma nova sessão será criada para cada requisição e fechada automaticamente após o término do processamento.

  • session.query() utilizado para consultar dados no banco.
    • session.query(User).all(): Retorna todos os registros de usuários, equivalente a SELECT * FROM users.
    • session.query(User).filter(User.id == user_id).first(): Busca o primeiro registro de usuário com o id correspondente a user_id.
  • session.add() adiciona um objeto à sessão, mas não persiste imediatamente no banco. Fica em pending, aguardando para ser inserido. Indica à sessão que a gravação ocorrerá em breve.
  • session.delete() marca um objeto para deleção, sem executar imediatamente no banco. A sessão registra a intenção de remover o objeto no próximo commit().
  • session.commit() efetiva todas as alterações pendentes na sessão para o banco de dados. Executa transações SQL e estabelece mudanças permanentes. Se ocorrer erro (como IntegrityError), a operação falha. Métodos Complementares ao commit:
    • session.refresh(db_user): Atualiza o objeto Python com dados novos gerados pelo banco após o commit, como id.
    • session.rollback(): Reverte as operações pendentes em caso de erro, restaurando a sessão a um estado consistente.
